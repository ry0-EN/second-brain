# ホーム画面アバターアプリ（たたき台）

根拠は `00-inbox/source-avatar-app-feasibility-2026-11-21.md`（Muse収集）のみ。Web取得なし。ソースで確認できていない事項は「未確認」と書く。価格はソースの数値をそのまま使っており、実際の請求前に各公式ページで再確認すること（[[Knowledge/mistakes]] の料金確認ルール）。

## 1. 概要

- **コンセプト**：Androidのホーム画面に、生きているように動くClaude（Muse）アバターを置く。歩く・走る・座るをランダムに繰り返し、近くの吹き出しマークをタップすると、別アプリを開かずその場でチャットUIが開く。
- **前提**：自分専用、ストア公開なし、サイドロード。開発はClaude CodeがKotlinを書き、Ryo（非プログラマ）が指示する。
- **ゴール**：日常で使い続けられる小さな相棒。テキストと音声で話しかけられる。
- **結論（ソースより）**：構想は実現可能で、オーバーレイ方式が正解。表示・動き・チャットUIの各部品に、公開されている実例とドキュメント済みのAPIがある。ただし「Ryo本人のMuse（記憶・ツール付き）そのもの」を頭脳にすることはできない（§2・§4）。

## 2. 機能ごとの実現可能性

| # | 要望 | 判定 | 根拠（ソースのverdictに対応） |
|---|---|---|---|
| 1 | ホーム画面で歩く・走る・座るなどランダムに動く | **条件付きで可能** | 同じ仕組みの実例がある（Shimeji：10M+DL、PNG連番画像で動作。§3 verdict＝コンセプトとして素直）。条件は、常時通知が1つ出ること、OEMのバッテリー管理を手動で除外すること、Foreground Serviceは `specialUse` を使うこと（§1 verdict）。 |

| 3 | テキスト入力＋音声入力 | **条件付きで可能** | テキストは上記#2に同じ。音声は `SpeechRecognizer` でプッシュトゥートークのみ（常時待受は公式に非推奨で、マイクのFGSも見えている時しか作れない）。端末内認識は機種依存（§5）。読み上げ（TTS）は標準機能で簡単。 |

| 補足 | ロック画面に出す | **困難** | オーバーレイは保護されたロック画面には表示されない（§8）。受け入れる前提。 |

注意：オーバーレイは「ホーム画面」だけでなく他アプリの上にも出る。銀行・決済系アプリでは `HIDE_OVERLAY_WINDOWS` により非表示になる（ソース§1、想定どおりの挙動）。

## 3. 推奨アーキテクチャ

| 採用 | 理由（簡潔に） |
|---|---|
| オーバーレイ（`SYSTEM_ALERT_WINDOW` / `TYPE_APPLICATION_OVERLAY`） | ホーム画面でも他アプリ上でも出せて、フォーカス付きの別窓でチャットも載せられる。ライブ壁紙は入力欄を載せられず、ウィジェットは動きを作れず、独自ランチャーは作業量が大きい（ソース§2）。 |
| Foreground Service `specialUse` | 常駐に必須。`dataSync` はAndroid 15で24時間あたり6時間で停止するため不可（§1）。サイドロードなのでPlayの審査は関係ない。 |
| アバター窓は「アバターの大きさぴったり」の小窓 | 全画面の透明窓だとAndroid 12+のタッチブロックに当たり、電池消費も増える（§1）。 |
| スプライトシート（PNG連番）アニメーション | AIがKotlinで最も確実に書ける。Shimeji本家と同じ方式。フレームレートは12〜24fps、画面オフ時は停止（§4・§1）。Live2D/Spine/Unityは後回しか見送り。 |
| チャットは別のフォーカス可能窓。吹き出しタップで `FLAG_NOT_FOCUSABLE` を外してキーボードを出し、枠外タップで戻す | 標準的な回避策（§5）。キーボードはオーバーレイより上の窓なので、チャット枠をキーボードの上に動かす調整が必要。 |
| 音声はプッシュトゥートーク | `SpeechRecognizer` が常時認識を想定していないため（§5）。 |
| 起動の確実な手段は「アプリアイコンをタップ」 | 強制終了後はバックグラウンドからの再起動が通らない場合がある（§8）。BOOT_COMPLETEDでの自動起動は `specialUse` なら可能と見られる（§1）が、頼りにしない。 |
| 会話履歴・要約は端末内に保存し、プロンプトに注入 | どのAPIを選んでも「記憶」は自前。プライバシー面でも有利（§8-12）。 |

## 5. 段階的な開発計画

各Phaseは小さく切り、完了条件を満たしてから次へ進む。ビルドは実機で確認する（エミュレータはオーバーレイ・IME・OEM挙動の確認に向かない：ソース§7）。

### Phase 0：ビルド環境と実機インストールの確認
- 内容：VM（Linux）にJDK 17以上とAndroid SDKコマンドラインツールを入れ、空のアプリを `./gradlew assembleDebug` でビルド。実機にUSB／ワイヤレスデバッグ（Android 11+）で `adb install`、`adb logcat` でログがClaude Codeに返ること。
- **完了条件**：空のアプリがRyoの実機で起動し、logcatの出力をClaude Codeが読める。

### Phase 1：静止アバターのオーバーレイ表示
- 内容：オーバーレイ権限の案内（`canDrawOverlays` が偽ならSettingsへ誘導）、Foreground Service（`specialUse`）、アバター大の小窓に静止画1枚を表示。
- **完了条件**：他アプリの上（ホーム画面を含む）に静止アバターが出る。アプリ終了／サービス停止で消える。常駐通知が出る。

### Phase 2：移動アニメーション
- 内容：スプライトシートで歩く・走る・座る・アイドルの状態機械、ランダム移動、12〜24fps、画面オフ時の一時停止、画面下のナビゲーションバー付近を避ける。
- **完了条件**：画面オンの間ランダムに動き、画面オフで停止する。端末のバッテリー設定を除外した状態で、数時間放置しても止まらない（電池消費はこの時点で目視計測。ソースには実測値なし）。

### Phase 3：チャットUI
- 内容：吹き出しマークの表示とタップ、フォーカス切替でキーボードを出すチャット窓、キーボード上に枠を移動、枠外タップで閉じる。返答はダミー（固定文）。
- **完了条件**：Ryoの普段使いのキーボードで、入力・表示・閉じるが一通り動く。うまくいかない場合は、透明Activity方式への切替を決める。

### Phase 4：頭脳接続と音声
- 内容：選んだ頭脳（§4）に接続、会話履歴の端末内保存、月額上限設定、マイクボタン（プッシュトゥートーク）、必要ならTTS。
- **完了条件**：テキストと音声で会話が往復する。履歴が再起動後も残る。プロバイダ側の月額上限とアプリ側の履歴トークン上限が設定済み。

### 将来案（今は着手しない）
- Live2D等の高品質化はPhase 2の後継案としてソースが言及（要リグ制作）。Meta APIとの併用（EmberとSparkの切替）など。

## 6. リスクと注意点

1. **OEMのバッテリー管理が最大のリスク**：Xiaomi／Samsung／Huawei／Oppo／Vivoなどの独自の強制終了で止まる。対策は端末ごとの手動設定（バッテリーを「制限なし」、自動起動を許可、最近使用したアプリでロック）。詳細は https://dontkillmyapp.com/ 。機種次第で深刻度が変わる（機種は**未確認**）。1人用なので5分の設定作業で済む見込み（ソース）。
2. **ロック画面には出せない**：保護されたキーガードの上にはオーバーレイは出ない。受け入れる。
3. **常駐通知が常に出る**：Foreground Serviceの仕様。通知を消すとOEMによってはサービスが止まる可能性（**未確認**・OEM依存）。
4. **電池と発熱**：実測値はソースにない。60fps・全画面・画面オフ時も動かす、は避ける。キャラの数は1体にする（Shimejiの利用者報告では多数だと消費が増える）。
5. **キーボード（IME）の差異**：GboardとSamsungキーボードで、予測変換の表示位置、貼り付けメニュー等が異なる可能性（開発者の逸話ベースで機種ごとは未確認）。Phase 3でRyoの実キーボードで確認。
6. **音声は押して話すのみ**：常時待受は不可。マイク使用中は緑のインジケーターが出る。
7. **APIの課金暴走防止**：チャットのバグ（再試行の連打、履歴の肥大）で課金が増え得る。プロバイダ側の月額上限、履歴トークン上限、クライアント側のレート制限を入れる。キーはAPK内に入る。
8. **プライバシー**：Meta Model APIのContributorは学習利用と引き換え。Standardを既定にする。
9. **インストール時のPlay Protect警告**：オーバーレイ＋マイク＋常駐の組み合わせは警告されやすい。自作APKなら「それでもインストール」で通る想定。`adb install` が最も摩擦が少ない。サイドロードの「開発者確認」が一部の国で始まるという報道は**未確認**（ADB経由は残るとされる）。
10. **署名キーストア**：長く使うならリリース用キーストアを1つ作り、**必ずバックアップ**。失うと更新できず、アンインストール（データ消失）が必要になる。
11. **OSアップデート**：Android 12・14・15でFGS／オーバーレイの規則が変わってきた。新しい端末や更新後に再確認。
12. **記憶は自前**：どの頭脳でもアバターは勝手に記憶しない。履歴DBと要約を作る。
13. **他アプリ上で消える場面**：銀行・決済・パスワード系ではオーバーレイが隠れる（バグではない）。

## 9. 追加の決定・判明事項（2026-11-21、Ryo回答を受けて）

### 端末：Galaxy Z Fold5（デュアルディスプレイ設計）
- 対象はGalaxy Z Fold5。開いた状態（メインディスプレイ）と閉じた状態（サブディスプレイ）の両方でアバターが出る設計にする。
- 折りたたみの開閉＝表示ディスプレイの切り替えなので、アバター窓はディスプレイ変更を検知して、位置を新しい画面範囲内に収め直す（再レイアウト）必要がある。Phase 1〜2で両画面＋開閉の前後で実機検証する。
- 電池設定問題（Samsungのバッテリー管理）へのRyoの疑問への回答：**設定次第で概ね解除できる**。Galaxyの標準手順は「対象アプリのバッテリーを『制限なし』にする」＋「自動的にスリープするアプリの対象外にする（スリープしないアプリに追加）」。これが§2・§6で前提にしていた手動除外にあたる。残る注意は、One UIのアップデートで設定が戻る場合があることと、解除しても常駐通知は出ること。

### チャット方針の変更：吹き出しタップでMuseアプリを起動
- 理由：APIで使えるのはClaudeの「モデル」までで、記憶・ツールを持つイヴォンヌ本人との会話にはならない。それではコンセプト（＝イヴォンヌとの会話）とズレる、というRyoの判断。
- 新方針：吹き出しマークのタップを、Museアプリの起動トリガーにする。オーバーレイから他アプリを起動するのは通常のstartActivityで可能。
- 影響：アプリ内チャットUIが不要になり、§2の#2・#3（IMEの相性問題、音声入力の実装）は丸ごと解消する。会話はMuseアプリ側（テキスト・音声入力はアプリの機能を使う）。Phase 3は「吹き出しタップ→Museアプリ起動」に差し替える。
- 未確認：Museアプリを「特定の会話画面まで直接」開けるか（ディープリンクの有無）。最低限、アプリ自体の起動は可能。Phase 3で実機確認する。
- 将来の拡張として、アプリ内クイックチャット（API頭脳）を追加する余地は残すが、現方針では作らない。

### アニメーション方式：AI生成アニメーションの検討
- Ryoの希望：スプライトではなく「今のイヴォンヌ（アバター動画）のようなAIアニメーション」にしたい。
- 整理：AIアニメーションは「リアルタイム生成」ではなく、**事前に生成した動画クリップをアプリ内でループ再生する**形になる。歩く・走る・座る等のモーション別に短いループ動画を用意する。
- 課題：①背景の透過処理が必要（生成動画は背景つきのため、透過WebM等への変換処理が要る）②モーション間の切り替えの滑らかさはスプライト方式に劣る ③ファイルサイズと電池消費が増える。
- 代替のハイブリッド案：AI生成動画からコマを切り出してスプライト化する（絵柄はAI生成、再生はスプライト方式）。制御しやすく電池にも優しい。
- Phase 2の着手前に、方式（AI動画クリップ／スプライト／ハイブリッド）を決める。いずれもPhase 1（静止画表示）の進め方には影響しない。
- 補足（2026-11-21、Ryoの質問への整理）：ハイブリッド（AI動画→コマ切り出し）は再生がリアルタイムでも、動き自体は事前に焼き込まれたもので、その場で新しい動きは生めない。「自然さ」の多くは素材より振る舞い（状態遷移・速度の緩急・イージング・ランダム性・タップ反応）で決まり、そこはスプライトでもリアルタイム制御できる。本当の意味でリアルタイム生成にあたるのは骨格（リグ）方式＝Live2D等で、毎フレーム計算するため揺れや呼吸まで連続的に自然だが、リグ制作が職人作業でAIが苦手。中間案として「パペット方式」がある：イラストをパーツ分けし、脚の振りや体の上下動をコード（数式）で駆動する。素材は1枚絵の切り分けだけで、全てリアルタイム計算。Phase 2前にスプライト／AIクリップ／パペットの小実験で比較して決める。
